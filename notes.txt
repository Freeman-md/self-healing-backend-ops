- Currently signals in evidences are just text. For the baseline recovery engine and future purposes, the LLM incharge of interpreting these signals should be aware of possible signal shapes from evidence collected. For example database_connectivity for issues with database connections rather than database_connection. This could lead to unresolved known issues as a result of naming conflicts. Same applies to incidents. The LLM / Evidence normalizer is also not constrained to the set of possible signals / incident types to classify an evidence against (multiple signals possible). This is just to ensure the baseline recovery engine can recover from known issues. The agentic layer might be flexible considering the fact that it's an LLM and has got another reasoning layer. Regardless, signals and incident types need to be stored, such that repeated issues can be resolved and new ones are also logged accordingly. This can also support the self-healing capabilities of the system whereby while certain issues might not have been resolved in the past, after having stored the signal or the incident type, the agentic layer can reason around the problem and suggest a suitable action or set of actions to take which already exist in the action registry. It's more like our agents are equipped with the tools and sent to the battlefield to conquer unforeseen situations / issues. Then, if they can't, they escalate. Humans then resolve the issues, and give the agents more capabilities to be able to resolve such issue again in the future without having to escalate. That's the whole purpose of the system. Yes, we start with baseline recovery. But the agentic layer is the proper self-healing part. A capable agent with tools thrown into fire to quench it and if it can't for that particular situation, it escalates. Next case with similar parameters will no longer need escalation because the agent would have learnt from the human feedback.
